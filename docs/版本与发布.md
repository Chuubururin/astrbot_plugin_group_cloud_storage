# 版本与发布

> 版本号遵循[语义化版本 2.0.0](https://semver.org/lang/zh-CN/)（`主版本.次版本.修订号`），
> 唯一定义在 `metadata.yaml` 的 `version` 字段；tag 格式 `vX.Y.Z`；发布由 tag 推送自动完成。

## 版本号口径

| 位 | 何时递增 | 示例 |
| --- | --- | --- |
| 主版本（X） | AstrBot 版本约束变更（`astrbot_version` 升档）、存储/接口不兼容变更（meta.db 需迁移且旧数据不可用）、配置键删除或语义反转 | `1.0.0` 起新纪元 |
| 次版本（Y） | 新功能：新命令、新 REST 端点、新 Tab、新配置项、新转存目标 | `0.1.0` |
| 修订号（Z） | 缺陷修复、性能优化、文档纠错、纯内部重构（无行为差异） | `0.0.8` |

预发布版本在修订号后加连字符标识，如 `v0.1.0-rc.1`；CI 自动将其发布为 GitHub 预发布（prerelease）。

> 0.x 阶段（当前）：API 与数据格式仍在快速演进，主版本恒为 0；不兼容变更递增次版本
> （如 `0.1.0` → `0.2.0`），并在提交信息与 release note 中明示迁移注意事项。

## 分支模型

- **dev**：日常开发分支，可直接 push；push 时 CI 自动运行。
- **main**：稳定分支，受保护——只能经 dev→main PR 合入，且 PR 的四项检查
  （`lint` / `python-tests` / `frontend-tests` / `contract-checks`）全部通过才允许合并。

dev→main 的同步由 `.github/workflows/promote-dev-to-main.yml` 自动完成：

- dev 上出现提交标题匹配 `chore(release): vX.Y.Z`（发布）或 `[merge]`（非发布同步）的提交时，
  workflow 自动创建（或复用）dev→main PR，等待检查全绿后合并；
- 失败时保留 PR 供排查，不会自动重试；
- 也可在 Actions 页手动触发（可选 merge / squash / rebase 合并方式）。

## 发布流程（walkthrough）

以发布 `0.0.8` 为例：

1. **更新版本号**：把 `metadata.yaml` 的 `version: 0.0.7` 改为 `0.0.8`（手改即可，
   不用脚本）。
2. **提交并推送 dev**：
   ```bash
   git checkout dev
   git add metadata.yaml
   git commit -m "chore(release): v0.0.8"
   git push origin dev
   ```
3. **等待自动 promote**：promote workflow 建 PR 并在检查全绿后自动合并到 main
   （可在 Actions 页或 PR 列表查看进度）。
4. **打 tag 并推送**（tag 必须打在 main 上）：
   ```bash
   git fetch origin main
   git tag v0.0.8 origin/main
   git push origin v0.0.8
   ```
5. **自动发布**：release workflow 依次执行——
   - 校验 tag 与 `metadata.yaml` 版本一致、tag 在 main 历史内；
   - 重跑全部 CI 检查（ruff / pytest / 前端单测 / 契约检查）；
   - 复用 `scripts/release.sh` 打包（staging + manifest.json + sha256 复检），
     产物命名 `astrbot_plugin_group_cloud_storage-v0.0.8.zip`，附 `.sha256` 校验文件；
   - 从 `git log` 生成中文 release note（上一 tag 到本 tag 的提交清单 + compare 链接），
     连同 zip 发布 GitHub Release。

预发布演练：流程相同，tag 用 `v0.1.0-rc.1`（记得 `metadata.yaml` 同步为 `0.1.0-rc.1`），
产出为预发布版本，不打扰正式用户。

## CI 结构

| Workflow | 触发 | 职责 |
| --- | --- | --- |
| `ci.yml` | push dev / PR 到 main·dev | 四项检查：ruff 0.16.6、pytest tests/unit、前端单测（node --test）、导入契约 + 架构测试 |
| `promote-dev-to-main.yml` | push dev（发布/`[merge]` 提交）、手动 | 建 dev→main PR → 等检查全绿 → 合并 |
| `release.yml` | push `v*` tag | 版本一致性校验 → 全量检查 → 打包 → GitHub Release |

设计要点：

- 全程只用内置 `GITHUB_TOKEN`，无需配置任何 secret；promote PR 的 CI 依赖
  `ci.yml` 同时监听 `push: dev`（PR head SHA 与 dev 提交 SHA 相同，分支保护按 SHA 识别检查）。
- 已知现象：GITHUB_TOKEN 创建的 PR 上，`pull_request` 事件的 CI 运行偶发启动失败
  （GitHub 提示 workflow file issue，无 job 产生）。这不影响发布链路——分支保护要求的
  四项检查由同 SHA 的 `push: dev` 运行提供（恒可运行），promote 轮询也只认这四项。
  手动创建的 PR（用户 token）不受影响。
- 发布包内容与 `scripts/release.py` 的 staging 规则一致：仅生产文件 + `manifest.json`
  （逐文件 sha256），不含测试/文档/运行时数据。
- `concurrency` 保证同一分支/同一 tag 的运行串行，过期的 CI 运行自动取消。

## 分支保护配置

已在 GitHub 仓库设置中启用（Settings → Branches）：

- **main**：Require a pull request before merging（审批数 0）；
  Require status checks = `lint`、`python-tests`、`frontend-tests`、`contract-checks`；
  禁止 force push 与删除。
- **dev**：仅禁止 force push 与删除（允许直接 push，push 时 CI 照跑）。

如需重建（API 方式）：

```bash
gh api -X PUT repos/{owner}/{repo}/branches/main/protection \
  --input - <<'JSON'
{
  "required_status_checks": {
    "strict": false,
    "contexts": ["lint", "python-tests", "frontend-tests", "contract-checks"]
  },
  "enforce_admins": false,
  "required_pull_request_reviews": {
    "required_approving_review_count": 0,
    "dismiss_stale_reviews": false
  },
  "restrictions": null,
  "allow_force_pushes": false,
  "allow_deletions": false
}
JSON
```

> `enforce_admins: false` 表示管理员（仓库所有者本人）可越权直推 main——单人维护期间
> 保留此逃生门；仓库公开协作后建议改为 `true` 并补 CODEOWNERS。
